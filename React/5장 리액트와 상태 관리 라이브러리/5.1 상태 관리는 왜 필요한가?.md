## 5.1 상태 관리는 왜 필요한가?

💡**웹 애플리케이션에서 상태**: 어떠한 의미를 지닌 값이며 애플리케이션의 시나리오에 따라 **지속적으로 변경될 수 있는 값**
e.g. UI, URL, form, 서버에서 가져온 값

웹 서비스에서 점차 다양한 기능이 제공됨에 따라 웹 내부에서 관리해야 할 상태도 점차 비례해서 증가
→ 상태를 효율적으로 관리하고, 상태가 필요한 쪽에서는 빠르게 반응할 수 있는 모델에 대한 고민

### 리액트 상태 관리의 역사

1. **Flux 패턴의 등장**

   ![image](https://github.com/user-attachments/assets/9fc85b4a-5c2f-456c-ade4-f1fb7ff46813)


   - **기존 MVC 패턴**: 양방향 데이터 바인딩으로 \*\*\*\*모델과 뷰가 많아질 수록 복잡도가 증가

   ![image](https://github.com/user-attachments/assets/65483681-ed8b-4d9e-a0fc-075f14f4383b)


   - **Flux 패턴**: 단방향 데이터 흐름을 변경하는 것을 제안

     - action: 어떠한 작업을 처리할 액션과 액션 발생 시 함께 포함시킬 데이터
     - dispatcher: 액션을 스토어에 보내는 역할, 콜백 함수 형태
     - store: 실제 상태에 따른 값과 상태를 변경할 수 있는 메서드를 가짐
     - view: 컴포넌트에 해당하는 부분으로 스토어에서 만들어진 데이터를 가져와 렌더링

     ```tsx
     type StoreState = {
     	count: number
     }

     type Action = { type: 'add'; payload: number }

     function reducer(prevState: StoreState, action: Action) {
     	const { type: ActionType } = action
     	if (ActionType == 'add') {
     		return {
     			count: prevState.count + action.payload,
     		}
     	}

     	throw new Error(`Unexpected Action [${ActionType}]`)
     }

     export default function App() {
     	const [state, dispatcher] = useReducer(reducer, { count: 0 })
     	function handleClick() {
     		dispatcher({ type: 'add', payload: 1})
     	}

     	return (
     		<div>
     			<h1>{state.count}</h1>
     			<button onClick={handleClick}+</button>
     		</div>
     	)
     }
     ```

     단점: action과 dispatcher를 모두 코드로 작성해야 하므로 **보일러 플레이트 코드 증가**
     장점: 데이터의 흐름은 모두 액션이라는 단방향이므로 **데이터 흐름의 추적이 쉬움**

   ⇒ Flux 패턴을 따르는 다양한 라이브러리들이 등장

2. **시장 지배자 Redux의 등장**

   Redux는 최초에는 Flux 구조를 구현하기 위해 만들어진 라이브러리였으나 여기에 _Elm 아키텍처를 도입_

   (Elm: model, update, view를 가지고 데이터 흐름을 세가지로 분류하고 이를 단방향으로 강제)

   - 장점: 하나의 글로벌 객체 상태 객체를 통해 이 상태를 하위 컴포넌트에 전파할 수 있음
     → props drilling 문제 해결 가능
   - 단점: action, creator, dispatcher, selector 등등을 모두 정의해야해서 보일러플레이트가 너무 많음

3. **Context API와 useConext**

   리액트 16.3에서 전역 상태를 하위 컴포넌트에 주입할 수 있는 새로운 **Context API 출시**

   → props로 상태를 넘겨주지 않더라도 원하는 곳에서 Context Provider가 주입하는 상태 사용 가능

   - 하지만 Context API는 **상태 관리가 아닌 주입을 도와주는 기능**이며, 렌더링을 막아주는 기능 또한 존재하지 않음

4. **훅의 탄생, 그리고 React Query와 SWR**
   - 훅 API로 인해 함수 컴포넌트에서 state를 매우 손쉽게 관리하고 재사용할 수 있게 됨
   - SWR, React Query: 외부에서 데이터를 불러오는 fetch를 관리하는데 특화된 라이브러리
5. **Recoil, Zustand, Jotai, Valtio에 이르기까지**
   - 페이스북 팀에서 만든 Recoil을 필수로 다양한 상태 관리 라이브러리 등장
